# AUTH.md — نظام تسجيل الدخول والـ RBAC في `ont27`

بُني بتاريخ 2026-07-30. يوثّق هذا الملف كل قرار معماري اتُّخذ، وكل نقطة تحتاج تأكيداً من صاحب المنتج قبل الاعتماد الكامل على النظام في الإنتاج.

## 1) القرار المعماري: Vercel Serverless Functions، مش Next.js Route Handler

`ont27` هو **Vite React SPA** (وليس Next.js) — تأكد من `package.json`/`vite.config.ts` قبل البناء. لا يوجد `app/` أو `pages/` بمعنى Next.js. المكافئ الصحيح لـ "Route Handler داخل نفس المشروع" هنا هو **Vercel Serverless Functions** تحت `/api/*`:

```
api/
  _lib/            # كل منطق مشترك (لا يُنشر كـ endpoint بذاته)
    env.ts         # قراءة متغيرات البيئة الخادمية فقط
    crypto.ts      # sha256 hex، AES-256-GCM لتشفير أسرار TOTP، مقارنة زمن ثابت
    jwt.ts         # توقيع/تحقق access + stage tokens (jose، HS256)
    cookies.ts     # قراءة/كتابة httpOnly cookies يدوياً
    supabase.ts    # عميل service_role — خادمي فقط، لا يصل للمتصفح أبداً
    session.ts     # إصدار/تدوير الجلسات (access + refresh)
    rbac.ts        # قراءة role_page_permissions
    guard.ts       # requireAuth() لأي endpoint محمي مستقبلاً
    totp.ts        # توليد/تحقق TOTP + أكواد الاسترداد (جاهز، غير مُفعّل حالياً)
    http.ts        # مساعدات JSON response موحّدة
  auth/
    login.ts       # POST /api/auth/login
    refresh.ts     # POST /api/auth/refresh
    logout.ts      # POST /api/auth/logout
    me.ts          # GET  /api/auth/me
    2fa-setup.ts   # POST /api/auth/2fa-setup   (غير مستخدم في تدفق الدخول حالياً)
    2fa-enable.ts  # POST /api/auth/2fa-enable  (غير مستخدم في تدفق الدخول حالياً)
```

هذا يحقق نفس الهدف من التوصية الأصلية: منطق الجلسة كله في مكان واحد، الاتصال بـ Supabase عبر service role من جهة الخادم فقط، ولا تعقيدات CORS/cookie-domain — لأن `/api/*` و الواجهة على نفس الأصل (`ont27.vercel.app`).

`vercel.json` مُعدَّل ليستثني `/api/*` من إعادة التوجيه الخاصة بالـ SPA (`/((?!api/).*)`) بدل الالتقاط الكامل القديم، وإلا كانت طلبات الـ API ستُعاد توجيهها لـ `index.html`.

## 2) قرار مُنتَج: 2FA غير مفعّل عند تسجيل الدخول حالياً (2026-07-30)

**الطلب الأصلي كان يفرض 2FA على أي دور بصلاحية `can_approve`.** تم بناء هذا المسار بالكامل (فحص `role_page_permissions`، توجيه لتسجيل أول مرة عند غياب صف `panel_users_2fa`، تحقق TOTP + أكواد استرداد)، ثم جاء توجيه صريح من صاحب المنتج أثناء التنفيذ: **"No 2fa"** — تعطيل الاشتراط فوراً.

- `api/auth/login.ts` الحالي: **لا يفحص 2FA إطلاقاً**. نجاح كلمة المرور = جلسة كاملة مباشرة.
- كود التسجيل (`2fa-setup.ts`, `2fa-enable.ts`) والجداول (`panel_users_2fa`) **باقية كما هي وجاهزة** — لم تُحذف. إعادة تفعيل 2FA لاحقاً تحتاج فقط استرجاع الفرع المحذوف من `login.ts` (كان موجوداً في نسخة أقدم من هذا الملف بنفس الجلسة — أو إعادة بنائه: فحص `roleRequires2FA(role)` من `_lib/rbac.ts` قبل `issueSession`).
- **الأثر المباشر:** هذا يحل مشكلة `Mody` (و`Ahmed` و`minafx2@gmail.com\`) الذين كانوا سيُحوَّلون لتسجيل 2FA أول مرة بدل تسجيل دخول مباشر — الآن يدخلون مباشرة بكلمة المرور فقط.
- ⚠️ **قبل أي إطلاق فعلي على بيانات حقيقية بمبالغ**: أعد تقييم هذا القرار مع صاحب المنتج. الأدوار `super_admin` (26 صفحة `can_approve`)، `operator`، و`operations_admin` (3 صفحات `can_approve`) هي التي تنفّذ approve/decline على معاملات مالية — تعطيل 2FA عليها فجوة أمنية حقيقية، وليست مجرد تفصيل تقني.

## 3) تشفير كلمة المرور — الحقيقة المؤكدة والفجوة المتبقية

فُحص `panel_users.password_hash` مباشرة على القاعدة الحية:

- **64 حرف hex** (وليس bcrypt/argon2 كما افترض الطلب الأصلي أو كما ورد في مرجع `api-reference-v3` عن نظام مختلف تماماً) → هذا نمط **SHA-256** الخام.
- **لا يوجد عمود salt** في `panel_users`. `eslam` و`Mody` لديهما **نفس القيمة بالضبط** في `password_hash` — أي نفس كلمة المرور بالضبط، وهذا لا يتفق إلا مع تجزئة بدون ملح عشوائي per-user.
- جُرِّب حل القاموس (~25 كلمة مرور شائعة/محتملة بالعربي والإنجليزي مع `sha256(password)` مباشرة) على الخمس حسابات — **لا تطابق**. هذا متوقع (كلمات المرور الحقيقية معروفة لصاحب المنتج فقط) ولا ينفي أو يؤكد وجود "pepper" إضافي.

**التنفيذ الحالي** (`api/_lib/crypto.ts::verifyPassword`): `sha256(PANEL_PASSWORD_PEPPER + password)` بمقارنة زمن ثابت، حيث `PANEL_PASSWORD_PEPPER` فارغ افتراضياً (= `sha256(password)` مباشرة).

**🔴 الفجوة التي لا يمكن حسمها بدون اختبار فعلي:** إن كان النظام القديم يستخدم pepper أو ترتيب مختلف (`sha256(password + secret)` بدل `secret + password`، أو تشفير مزدوج)، فسيفشل تسجيل الدخول لكل المستخدمين رغم صحة كلمة المرور. **الخطوة الإلزامية بعد النشر:** جرّب دخول `Mody` (أو أي حساب) بكلمة مروره الحقيقية المعروفة لصاحب المنتج. لو فشل رغم صحة كلمة المرور:
1. تأكد أولاً أن `password_hash` نفسه لم يتغيّر (لم نُعدّله ولن نُعدّله بدون توجيه).
2. جرّب `sha256(password + pepper)` بدل `sha256(pepper + password)` — عدّل ترتيب الدمج في `verifyPassword`.
3. لو معروف مصدر الهجرة الأصلي (السكريبت الذي أنشأ هذه الـ hashes)، ارجع له مباشرة بدل التخمين.

**لم نُنشئ مستخدمين جدد ولم نُعدّل أي `password_hash` موجود** — طبقاً لتوجيه الطلب الصريح.

## 4) اسم المستخدم `minafx2@gmail.com\` — لم يُصحَّح

القيمة في القاعدة فعلاً `minafx2@gmail.com\` (بـ backslash زائد في النهاية، تم التحقق مباشرة عبر SQL). **لم نُعدّله** — القرار متروك لصاحب المنتج: هل هو خطأ إدخال يُصحَّح إلى `minafx2@gmail.com`، أم مقصود؟ تسجيل الدخول يعمل بهذه القيمة بالضبط (مطابقة case-insensitive، الـ backslash جزء من السلسلة وليس رمز إفلات).

## 5) قواعد تسجيل الدخول المُطبَّقة فعلياً

- **حساس لحالة الأحرف؟ لا.** البحث عبر `lower(username) = lower(btrim(input))` (دالة `panel_get_user_for_login` في القاعدة، `SECURITY DEFINER`). أُضيف `unique index on lower(username)` لمنع أي تصادم حالة أحرف مستقبلي (لا يوجد تصادم حالياً).
- **القفل:** 5 محاولات فاشلة → `locked_until = now() + 15 دقيقة`. رسالة صريحة `account_locked` (HTTP 423) بدل رسالة عامة، لأن هوية المستخدم مؤكدة بالفعل في هذه المرحلة.
- **رسائل الخطأ الأخرى:** موحّدة `invalid_credentials` (HTTP 401) — لا تكشف هل الخطأ في اسم المستخدم أو كلمة المرور أو أن الحساب غير نشط (`active=false`).
- **عند نجاح الدخول:** يُصفَّر `failed_login_count`، يُحدَّث `last_login_at`، يُصدَر access JWT (20 دقيقة) + refresh token عشوائي 256-bit (7 أيام، يُخزَّن كـ SHA-256 hash فقط في `panel_refresh_tokens`)، يوضعان في httpOnly cookies.
- **تدوير الـ refresh token:** كل استخدام لـ `/api/auth/refresh` يُبطل التوكن القديم (`revoked_at` + `replaced_by`) ويصدر واحداً جديداً — استخدام واحد فقط لكل توكن. إعادة استخدام توكن مُبطَل بالفعل تُبطل **كل** توكنات المستخدم فوراً (كشف سرقة).
- **Cookies:** `httpOnly`, `Secure`, `SameSite=Strict`. اختيار `Strict` وليس `Lax` لأن الواجهة و`/api/*` على نفس الأصل تماماً (`ont27.vercel.app`) — لا حاجة لأي تدفق cross-site.

## 6) JWT المخصص

- السر: `PANEL_AUTH_JWT_SECRET` — متغير بيئة مستقل تماماً، **لا علاقة له بأي سر Supabase**. يُولَّد بـ `openssl rand -base64 48`.
- الـ payload: `{ typ: 'access', user_id, username, role, iat, exp }`، صلاحية 20 دقيقة.
- تجديد صامت: الواجهة تستدعي `/api/auth/refresh` كل 15 دقيقة تلقائياً (`AuthContext`)، وأيضاً عند أي 401 غير متوقع (لاحقاً عند بناء طبقة fetch مركزية للصفحات المحمية).

## 7) RBAC

- `role_page_permissions` هو مصدر الحقيقة الوحيد. `_lib/rbac.ts::authorize(role, page, action)` يُستخدم من أي endpoint محمي مستقبلي عبر `_lib/guard.ts::requireAuth(req, res, { page, action })`.
- `/api/auth/me` يرجع مصفوفة الصلاحيات كاملة للدور الحالي — الواجهة تستخدمها عبر `useAuth().can(page, action)` لإخفاء/تعطيل عناصر الواجهة، **لكن الفحص الحقيقي والملزم أمنياً يبقى دائماً في الخادم** (كل endpoint جديد لصفحة محمية يجب أن يستخدم `requireAuth` بنفسه، وليس الاعتماد على إخفاء الواجهة فقط).

## 8) ما لم يُبنَ بعد (خارج نطاق هذه المهمة)
