1. System Overview

OnTarget PSP is a payment service provider API for processing payin (deposit) and payout (withdrawal) transactions in Egypt and MENA markets.

Architecture & Stack

API Server
Node.js · Express 4 · Railway
Database & Auth
Supabase · PostgreSQL 17 · RLS
Checkout Frontend
Vanilla HTML/JS · Vercel
File Storage
Supabase Storage · payment-proofs bucket
DB Schema
ontarget (8 tables, all RLS-enabled)
DB Access Pattern
All DB ops via SECURITY DEFINER RPCs only

Base URLs

EnvironmentAPI BaseCheckout Base
Production https://ontarget-api-v3-production.up.railway.app https://checkout.ontarget-egy.com
Local Dev http://localhost:3000 http://localhost:5500
All endpoints are prefixed with /v1. Example: POST https://ontarget-api-v3-production.up.railway.app/v1/checkout/create

Supported Currencies

EGP · USD · EUR · SAR · AED · KWD · BHD · OMR · QAR

Payment Flows

Payin (Deposit)

1
Merchant creates checkout
POST /v1/checkout/create → receives secure checkout_url
2
Customer opens checkout URL
256-bit token in URL; 15-min session timer starts
3
Customer selects payment method
Sees merchant wallet details (Vodafone Cash, InstaPay, etc.)
4
Customer transfers & submits proof
POST /v1/payment/submit with name, account, screenshot
5
Merchant approves or declines
PATCH /v1/transaction/:id/status → webhook fired

Payout (Withdrawal)

1
Merchant creates payout
POST /v1/payout/create → receives secure payout_url
2
Merchant shares link with customer
Or embeds as iframe in their portal
3
Customer opens payout URL
Green-themed page; customer sees amount they'll receive
4
Customer submits their account
POST /v1/payment/payout with method, account, name
5
Merchant processes transfer
Sends money externally, then approves via dashboard

2. Authentication

Three auth methods are supported: JWT Bearer tokens (merchant portal), API key (machine-to-machine), and Admin Secret (dashboard).

POST /v1/auth/merchant/refresh Public
Exchange a refresh token for a new access + refresh token pair. Old refresh token is immediately invalidated (rotation).

refresh_tokenstring✓ requiredThe refresh token from login

Revoke the current session. Add Authorization: Bearer <access_token> header.

2.2 API Key Auth (Machine-to-Machine)

Send X-API-Key: ot_live_xxxxxxxx in the request header. Used for server-to-server integration (checkout creation, transaction status checks). The raw key is shown only once at merchant creation; only its SHA-256+salt hash is stored in the database.

2.3 Admin Auth

Send X-Admin-Secret: <ADMIN_SECRET> header. Required for all /v1/admin/* endpoints. The admin secret must be at least 32 characters and is set via environment variable. Never expose it to clients.

}

Signature Verification

Every webhook includes an X-OnTarget-Signature header containing an HMAC-SHA256 of the raw request body signed with the merchant's secret_key (ot_secret_xxxxxxxx). 
// Node.js verification example
const crypto = require('crypto');

function verifyWebhook(rawBody, signatureHeader, secretKey) {
  const expected = crypto
    .createHmac('sha256', secretKey)
    .update(rawBody)
    .digest('hex');
  return crypto.timingSafeEqual(
    Buffer.from(expected),
    Buffer.from(signatureHeader)
  );
}
Retry policy: If your endpoint returns a non-2xx status, the webhook is not currently retried automatically. Ensure your endpoint responds 200 within 10 seconds.

10. Security Model

Multiple layers of protection from URL to database.

Checkout URL Token

PropertyValue
Generationcrypto.randomBytes(32) → 64-char hex string (256 bits)
StorageNever stored raw — only SHA-256(token) stored in checkout_token_hash column
LookupServer hashes incoming token via PostgreSQL sha256(token::bytea) and matches against stored hash
Brute-force cost2256 combinations — computationally infeasible
Expiry15 minutes from creation
Single-useEnforced atomically in DB via status check before any write

API Key Security

PropertyValue
Formatot_live_ + 40 hex chars (160 bits)
StorageSHA-256(key + SALT) — salt from environment variable
RotationImmediate — old key invalid the moment new key is generated

Single-Use Transaction Enforcement

1
Frontend (Checkout Page)
If status === 'processing' on page load → shows "already submitted" screen instead of form. No resubmit button.
2
API Layer (payment.js)
Checks transaction.status !== 'pending' before calling the RPC → returns HTTP 409 ALREADY_SUBMITTED immediately.
3
Database Layer (PostgreSQL RPC)
api_payment_submit and api_payout_submit are plpgsql functions that read the status atomically. If not pending, they RAISE EXCEPTION — transaction rolled back.

Rate Limiting

EndpointLimitWindow
All endpoints (global)100 requests15 minutes / IP
GET /v1/transaction/public30 requests1 minute / IP
POST /v1/payment/submit10 requests5 minutes / IP
POST /v1/payment/payout10 requests5 minutes / IP

Database Security

  • All 8 ontarget tables have Row Level Security (RLS) enabled
  • Public/anon roles cannot access any table directly
  • All access goes through SECURITY DEFINER RPCs with fixed search_path = ontarget, public
  • Sessions table: tokens stored as SHA-256 hashes only
  • Merchants table: API keys stored as SHA-256+salt hashes only
  • Passwords stored as bcrypt hashes (cost 12)

Transport & Headers

  • HTTPS enforced (Railway + Vercel both enforce TLS)
  • Helmet.js security headers on all API responses
  • CORS: production restricts origins to *.ontarget-egy.com and *.vercel.app
  • Token format validated (/^[0-9a-f]{64}$/) before any DB lookup
